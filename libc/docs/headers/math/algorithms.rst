==============================
Math Function Algorithm Design
==============================

.. default-role:: math

This page gives an overview of the common algorithmic techniques used across
LLVM libc's math function implementations.  For function-specific details, see
the dedicated pages linked from :ref:`math`.

.. contents:: Table of Contents
   :depth: 3
   :local:


Floating-Point Arithmetic Levels
================================

LLVM libc uses three levels of floating-point precision, chosen based on the
accuracy requirements at each stage of a computation:

Double (64-bit)
  The primary computation type.  Most intermediate results are computed in
  hardware double precision.

DoubleDouble (2 \times 64-bit)
  A pair of doubles ``{lo, hi}`` representing ``hi + lo`` with non-overlapping
  significands, giving roughly 107 bits of precision.  This is used for
  intermediate results in the *fast phase* when extra accuracy is needed without
  the cost of full software 128-bit arithmetic.

Float128 (128-bit ``DyadicFloat<128>``)
  A software floating-point type giving 128 bits of significand.  This is used
  in the *accurate phase* as a fallback when the fast phase cannot guarantee
  correct rounding.


Two-Phase Computation
=====================

Most double-precision math functions use a two-phase approach:

Fast phase
----------

1. **Range reduction**: Transform the input into a small interval where a
   polynomial approximation is effective.

2. **Polynomial approximation**: Evaluate a minimax polynomial (typically
   generated by `Sollya <https://www.sollya.org/>`_) in DoubleDouble arithmetic.

3. **Ziv's accuracy test**: Compute an error bound ``err`` on the
   DoubleDouble result ``r = r.hi + r.lo``, then check:

   .. math::

      \circ(r_{\text{hi}} + (r_{\text{lo}} - \text{err}))
      \stackrel{?}{=}
      \circ(r_{\text{hi}} + (r_{\text{lo}} + \text{err}))

   where `\circ` is the current rounding mode.  If both sides agree, the result
   is correctly rounded and we return immediately.

Accurate phase
--------------

When Ziv's test fails (the result lies near a rounding boundary), we redo the
computation in Float128 arithmetic.  This guarantees enough precision to
determine the correctly rounded double result for all inputs.

This two-phase design means that the expensive Float128 path is rarely taken -
typically for fewer than 1 in 10,000 inputs - while still achieving correct
rounding for all inputs in all four IEEE 754 rounding modes.


Range Reduction
===============

Range reduction is the process of transforming the input `x` into a small value
`u` where a polynomial can approximate the target function efficiently.  The
specific technique depends on the function family.

Additive reduction (sin, cos, tan)
----------------------------------

For periodic functions, we reduce modulo a fraction of the period:

.. math::

   k = \operatorname{round}\!\left(\frac{128 \, x}{\pi}\right),
   \qquad
   y = x - k \cdot \frac{\pi}{128}

so that `|y| \leq \pi / 256`.  Tabulated values of `\sin(k\pi/128)` and
`\cos(k\pi/128)` are combined with polynomial evaluations of `\sin(y)` and
`\cos(y)` via the angle addition formulas.

For small inputs (`|x| < 2^{16}`), the reduction is performed with a 3-part
representation of `\pi/128`.  For large inputs, an adaptive-precision table of
`128/\pi` is used to maintain accuracy.

See :ref:`trig_algorithm` for details.

Multiplicative reduction (log, exp)
-----------------------------------

For logarithms, the input is decomposed as
`x = 2^{e_x}(1 + m_x)` and a lookup table provides
`r \approx 1/(1 + m_x)` so that `u = r(1 + m_x) - 1` is small.
See :ref:`log_algorithm` for the full analysis.

For exponentials, similar reduction modulo `\ln 2` is used.

Algebraic substitution (asin, acos, atan)
-----------------------------------------

For inverse trigonometric functions, the domain is split into regions where
algebraic identities reduce the computation:

- For `|x| < 0.5`: direct polynomial on `x^2`
- For `0.5 \leq |x| < 1`: identities like
  `\operatorname{asin}(x) = \pi/2 - 2\operatorname{asin}(\sqrt{(1-x)/2})`
  transform the input into the small-argument regime
- For `\operatorname{atan}` with `|x| > 1`: the reciprocal identity
  `\operatorname{atan}(x) = \pi/2 - \operatorname{atan}(1/x)` is used

See :ref:`trig` for details.


Polynomial Approximation
=========================

LLVM libc uses minimax polynomials - polynomials that minimize the maximum
approximation error over the reduced interval.  These are typically generated
using the `Sollya <https://www.sollya.org/>`_ tool.

Key properties:

- **Degree selection**: balances accuracy and performance.  Typical degrees are
  6-20 for float functions, 9-13 for double functions.

- **Symmetry exploitation**: when the target function is odd (like `\sin` or
  `\operatorname{asin}`), only odd-degree terms are used.  When even (like
  `\cos`), only even-degree terms.

- **Evaluation** uses Horner's method or Estrin's method for efficient
  computation.

- **Lookup table indexing**: for functions like ``asin`` and ``atan``, the
  reduced argument `u` is further decomposed as `u = u_k + \delta` where
  `u_k = k/64` and `|\delta| < 1/128`.  Precomputed values at `u_k` are
  stored in a lookup table, and a polynomial corrects for `\delta`.


Exception Handling
==================

IEEE 754 requires specific behavior for special inputs and exceptional
conditions.  LLVM libc handles:

- **NaN and infinity propagation**: following C and IEEE 754 rules.
- **Domain errors**: setting ``errno`` to ``EDOM`` and raising
  ``FE_INVALID`` for inputs outside the mathematical domain (e.g.,
  `\operatorname{asin}(2)`).
- **Underflow**: raising ``FE_UNDERFLOW | FE_INEXACT`` when the result is
  subnormal, using IEEE 754 "after rounding" tininess detection.
- **Exact results**: e.g., `\sin(0) = 0`, `\operatorname{asin}(0) = 0`,
  returning without raising inexact.


GPU Mode
========

When compiled for GPUs, math functions use the ``LIBC_MATH_HAS_SKIP_ACCURATE_PASS``
flag, which disables the Float128 fallback and Ziv's test.  This trades
correct rounding for performance, producing results accurate to within a few
ULPs.  Additional GPU flags include:

- ``LIBC_MATH_INTERMEDIATE_COMP_IN_FLOAT``: use float instead of double for
  intermediates where possible.
- ``LIBC_MATH_SMALL_TABLES``: use smaller lookup tables to reduce memory
  pressure.
- ``LIBC_MATH_NO_ERRNO``: skip errno setting.
- ``LIBC_MATH_NO_EXCEPT``: skip floating-point exception handling.
